# Decision log

| # | Decision | Reason |
|---|----------|--------|
| D1 | npm workspaces monorepo: apps/web, apps/server, packages/{game-core,contracts,config}. Existing Vite scaffold moved to apps/web. | Spec §4 layout; preserves existing Tailwind v4 + Vite setup. |
| D2 | Tailwind v4 via `@tailwindcss/vite` (already installed) with tokens in `@theme`. | Reuse existing setup. |
| D3 | **Avatars are non-human customisable blobs** (body colour, eyes, glasses, headwear, cape/backpack) per the latest mockup; rendered by one SVG function used for HTML tiles and Phaser textures. This overrides spec §8/§15 "stylised human characters". | Explicit user override. Avoids human-likeness/modesty/sacred-figure issues. |
| D4 | One Postgres code path: `PgStore` over a minimal `Db` interface. Production = `pg` Pool → Supabase Postgres. Dev/test = PGlite (real Postgres in WASM), refused when `NODE_ENV=production`. | Verifies real SQL/migrations locally without credentials; avoids a divergent in-memory store. |
| D5 | Auth: server verifies Supabase JWTs with `jose` (JWKS or HS256 secret). `AUTH_MODE=dev` provides a local email/password auth for development only and is refused in production. | No Supabase credentials available; no mock disguised as Supabase. |
| D6 | Guest identity = random 256-bit opaque token, stored SHA-256-hashed, sent as `Authorization: Bearer` / socket `auth.token`, kept in `localStorage` (per room). No cookies → no CSRF; XSS risk mitigated by CSP + sanitised content. Multi-tab: same token → same participant; one active answer per round enforced by DB unique constraint. | Cross-origin Namecheap→Render deployment. |
| D7 | Room codes are 6 random digits (matches mockup "482 916"); rate-limited lookups; codes expire with the room. | Mockup parity, usability. |
| D8 | Answer window = `deadline`; server accepts submissions received ≤ deadline + `ANSWER_GRACE_MS` (750 ms), documented infrastructure allowance. Round closes after the grace. | Spec §11. |
| D9 | Per-player option order is a deterministic client-side shuffle from `shuffleSalt` + participant id; stable option ids a–d. Single broadcast per round. | Fairness + cheap fan-out. |
| D10 | Competing-host start requires ≥2 competitors. Competing host is a participant; audience host is not. Custom pack ⇒ audience mode (forced). | Spec §6. |
| D11 | Finale review window: after a summit/limit round is revealed, a hold (`FINALE_REVIEW_MS`, 8 s audience / 4 s competing) precedes finalisation. Audience host may void in it. | Spec §5. |
| D12 | Restart recovery: games in `question_open` go to `recovery pause`; on host resume the round re-opens with a fresh full window and prior accepted answers are retained. Scored/revealed rounds are never re-scored (guarded by round status transition). | Spec §11. |
| D13 | Solo practice runs over HTTP (server-authoritative per question deadline), using the same game-core scoring. | Simpler than sockets; no realtime need. |
| D14 | Redis is an optional `Cache` adapter (ioredis) used for rate-limit counters when `REDIS_URL` set; in-memory single-instance fallback otherwise. PostgreSQL stays authoritative. | Spec §14. |
| D15 | Email: Brevo REST adapter; `EMAIL_MODE=log` in dev prints the email and records it as *not sent*. | No credentials. |
| D16 | Landing/scene art are code-drawn SVG placeholders with an asset manifest; production art is documented in `docs/ASSETS.md`. | Spec §15; no image generation available. |
| D17 | ESLint: `no-explicit-any`, `only-export-components`, `set-state-in-effect` are warnings (48 remain) rather than errors; real findings (component-in-render, unused vars, ref writes) were fixed. | Page glue consumes loosely-typed API payloads; React 19's strictest advisory rules flag legitimate prefill effects. |
| D18 | Playwright e2e runs against the built web app with `TIMING_SCALE=0.3` and `eq:nogame=1` (HTML staircase) for two of three players. | Three simultaneous software-rendered WebGL scenes starve a CPU; Phaser is still exercised by the phone-sized player and by `tests/tools/probe.mjs`. |
| D19 | Lobby prefetches the lazy Phaser chunk; no live questions or answer data are preloaded. | Spec §9.9. |
| D20 | The generic Vite scaffold README was replaced by the project README; the scaffold itself was moved to `apps/web`. | Monorepo layout (D1). |
| D21 | Staircase redrawn to match the reference (hall, moonlit arch, glowing step edges, lanterns, side niches, step numbers on the right). Performance design: the whole backdrop is baked once per resize into one 2D-canvas texture; avatars are ≤28 small sprites (≤12 on low-power) with per-step caps and "+N" badges; render-on-demand (the Phaser loop sleeps when nothing moves, wakes for results/joins/resizes); no infinite tweens; canvas at CSS-pixel resolution; timers tick once per displayed second and the bar animates via transform. | User request: reference look without lagging low-end phones. Measured: idle page ≈ 0.7–0.9 % of one core in headless software-GL (was ≈ 17 % with a 4 Hz ring + CSS transition); scene idle ≈ 0.3 %. |
| D22 | House rules (host- or player-chosen, shown in the rules before anyone joins): **Super question** — exactly one per game, chosen at start from rounds 3..60 % (deterministic), announced to everyone when it opens; a correct answer climbs +2 (capped at the summit), a miss is the normal −1; if it is voided its replacement becomes the super question. **Gentle mode** — wrong/unanswered = stay put. Both default off ("Classic" is unchanged). Applies to live games and solo/Quick climb. | User request; supersedes the earlier spec line "no boosts" only for this opt-in, same-for-everyone twist. Elimination, points, streak boosts, power-ups and speed bonuses deliberately NOT built. |
| D23 | Reaction stickers: fixed set of five drawn icons (star, lantern, heart, spark, flame — no emoji, no clap), players only, between rounds only, 1 per 1.5 s each, batched into one broadcast. No free text. | User request + spec §12 (no public chat). |
| D24 | UX: intent-first landing (Quick climb / Join / Host), persistent "adventurer" (name+look) chip, rejoin banner, one-tap join, one-screen host setup with templates (sign-in only at Create, form preserved), docked invite panel in the lobby (separate share page kept only as a legacy route), journey strip, first-run coach tips, grid tiles instead of dropdowns for all player/host-facing choices (admin filters keep selects), reveal chart, positive-only round highlights, tension cues, streak badge (display only), recap card (share / save image) and a "What next?" strip built from real results only. | User-approved UX plan. |
| D25 | The landing hero reuses the in-game hall via a Phaser-free painter (`scene/hall.ts`) drawn once into a canvas, so the landing page still never loads the game engine. | Spec §9.1 + performance. |
| D26 | Sign-up uses **our own email one-time code** (Brevo API) instead of Supabase's email OTP: code → then account is created via the Supabase Admin API (service-role key, server-only) already confirmed; Supabase public sign-ups must be switched off. Codes: 6 digits, keyed-hash stored, 10 min, single use, 5 tries, 30 s cooldown, 5/hour/address; existing addresses get an "already registered" email and an identical-looking response. Password reset stays a Supabase link. | User request. Wins: Brevo directly, no junk accounts, fully testable locally (code shown in dev). Cost: a powerful server-only secret and one Supabase setting. |
| D27 | Browser tests are isolated from real credentials: `npm run test:e2e` builds the web app in dev-auth mode and the test server ignores `apps/server/.env` (`ELIMQUEST_SKIP_ENV_FILE=1`). | `apps/server/.env` now points at the real Supabase project. |
